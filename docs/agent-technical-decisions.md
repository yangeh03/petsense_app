## 1. Agent 运行时 · P05

**已确认优先验证 LangChain。** 推荐用 Python `create_agent` 与 LangGraph 执行模型和工具循环，PetSense Flask 承接鉴权、业务接口、消息与来源。运行由现有 Agent 域入口接入，模型在循环内根据上下文直接回答、澄清、选择工具、继续查询或结束。

| 候选 | 取舍 |
| --- | --- |
| LangChain `create_agent` | 优先候选。能在现有 Python 服务内接入工具、运行上下文和中间件。具体版本、模型适配和部署依赖需在 PetSense 集成环境验证。 |
| LangChain Deep Agents | 提供上下文压缩、文件系统和子任务等能力。现阶段需要额外收紧默认可见的文件和委派工具。下载超时阻塞了本轮运行探针，评估依据是官方文档。 |
| Pi Agent Core | TypeScript 工具循环、上下文转换和事件流都能满足基础需求。接入 Flask 会新增 Node/Bun 运行时与进程接口，可在独立 Agent 服务有明确需求时重评。 |
| 现有自研循环 | 适配开销低，已有线上使用证据。继续扩展会自行维护模型协议、预算、流事件、恢复和可观测性，适合作为迁移期可回退路径。 |

**P05 定型门槛。** 用同一套场景对比现有实现。验证真实 MiniMax 多轮工具执行、权限拦截、超时、失败交付与流事件。采集首字、完成耗时、调用数及消耗。新路径移除 `model.decide()` 前置分流和原话规则分支，保持现有会话与来源兼容；发布回退使用部署开关，按整个会话或版本切换，避免同一回合切换执行路径。 [LangChain Agents](https://docs.langchain.com/oss/python/langchain/agents) · [Deep Agents](https://docs.langchain.com/oss/python/deepagents/overview) · [Pi Agent Core](https://github.com/earendil-works/pi/blob/main/packages/agent/README.md)

## 2. 模型和供应商协议 · P03、P05

**现有模型基线。** 生产 G1 使用 MiniMax-M3.1-Flash 的国内端点。P03 保留服务器侧凭据和可配置模型 ID，记录具体端点、模型版本及测试条件。模型升级需要重跑行为与协议回归。

**P05 推荐验证的接入路径。** 优先验证 MiniMax 的 Anthropic 兼容入口与 `ChatAnthropic`。隔离探针以 LangChain 1.5.2、`langchain-anthropic` 1.7.12 和真实 MiniMax 跑通两轮工具调用、流事件、工具返回的来源数据及进程内会话检查点。首次回答曾虚称执行了写入，说明协议连通与回答事实约束需分别验收。上述依赖版本为探针记录，P05 根据本仓库锁文件和生产部署环境定型。

现有 OpenAI 兼容协议作为备选。若复用该通道，需验证适配器在多轮信息往返中保留 `tool_calls` 和 MiniMax 所要求的独立推理字段。P03/P05 以当前生产账户在隔离背景下完成实测，覆盖真实可用的工具调用、流式、终止原因、超时及限流；用合成数据验证协议，用授权的真实观测验收 PetSense 联调。 [MiniMax Anthropic SDK](https://platform.minimax.io/docs/api-reference/text-anthropic-api) · [MiniMax OpenAI SDK](https://platform.minimax.io/docs/api-reference/text-openai-api)

## 3. 结构化工具与交付 · P00、P01、P05、P06

**技术约束。** 模型负责理解自由文本、提出参数并选择动作。后端从授权上下文绑定主体和触发身份，对类型化参数、归属、窗口、预算、能力版本和侧作用执行校验。模型可见的工具 schema 只含业务必要参数，用户、宠物与访问范围由服务端注入。第一条集成链路复用既有观测查询的聚合和覆盖口径。

工具结果分两部分。模型收到用于推理的摘要，应用保留可信的来源数据，包括调用标识、适用主体、版本、时间区间、覆盖以及实际结果。模型的结构化交付可引用这些结果标识，后端校验引用并生成来源卡。统计数值取自真实结果字段或后端计算。来源区分观测、主人确认的资料、历史结果与外部网页。数据不足和调用失败以各自状态交付。解释标明观测与推断的区别，所用证据的可靠程度以已记录覆盖、样本、识别版本和已知限制说明。权限矩阵根据已登记工具、运行触发、授权和确认记录在操作前执行，模型对意图与范围的解释用于行为评测与审计。

显式角色选择及引用对象来自客户端元数据。模型可决定自动模式下的发言角色和是否补充。服务端按角色和内容块契约校验，客户端按存储的角色呈现。成功写入、计划生效和任务状态来自服务端回执。

**定型门槛。** P00 固定边界和引用语义。P05 对比模型原生结构化输出与工具 schema，锁定 MiniMax 实测通过的方案。验收覆盖模型生成无效来源、跨宠物调用、查询返回空与失败、混合内外部证据、多窗口、历史引用和显式指向。P06 核对来源跳转、角色呈现和重进恢复。 [LangChain Tools](https://docs.langchain.com/oss/python/langchain/tools) · [Structured Output](https://docs.langchain.com/oss/python/langchain/structured-output)

## 4. 工作上下文和执行检查点 · P02、P05、P13

**首轮建议。** 由现有 `AgentTurn`、主题、回复关系、档案、已确认设定和有效来源组装有界上下文。Agent 可按需查询更多证据。沿用 G1 最近 12 个已完成回合作为兼容起点，P05 按 token 预算和主题回归调整；当前话题的引用对象、有效确认和待处理状态应可稳定找回。合成摘要可辅助压缩，业务事实的来源继续引用其授权原记录。

**框架状态选型待验收。** 检查点存放模型执行状态及可恢复进度。产品会话持久数据、确认事实、任务计划和交付仍归 PetSense。进程内检查点只用于探针。初期可从持久回合重建对话并保持既有请求语义；P13 按真实重启与恢复场景决定生产检查点后端和生命周期。

**定型门槛。** P02/P05 验证新旧历史、主题间隔离、长对话截断、引用可找回和客户端断线重进。P13 验证进程重启、任务重新领取、部分完成后恢复及已提交副作用去重。 [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

## 5. 业务资料、长期记忆和检索 · P07–P10

**推荐 SQLAlchemy 与 PetSense 业务存储。** 宠物档案、助手设定、已确认事实、经历摘要、统计基线、目标计划各有真值和版本。记忆至少带授权主体、事实来源、发生时间或未知标记、确认状态及修订关系。主人能核对或纠正已知事实，修订需影响后续检索和回答。P07/P08 先定字段级写入和确认协议，P09 复用这些可信来源。P10 的有效日和统计基线由带覆盖与模型版本的观测计算。

首版按宠物、主题、日期、维度、类型和数据版本检索，沿用产品设计中的明细与汇总保留策略。选择外部向量存储需新增索引同步、归属与删除机制。待固定评测出现确切召回缺口，再评价全文检索、embedding 重排或向量索引。摘要先保留可回查来源及重新计算口径。历史修正与隐私删除的留存、重算和索引清理由 spec 明确。

**定型门槛。** P07/P08 通过确认、重复确认、拒绝、纠正和同宠物资料一致性，明确哪些字段可由当前明确授权直写。P09 验收跨天找回、数据缺口、纠正后召回、数据过期和按用户清理。P10 验证有效日、算法版本和可比性，覆盖不足时保持学习状态。 [LangChain Long-term Memory](https://docs.langchain.com/oss/python/langchain/long-term-memory)

## 6. 持久调度和自主运行 · P13–P16

**推荐现有数据库加有界 worker。** 服务端持久化到期时间、触发事实、目标版本、运行状态、重试与结果，借稳定业务键保证领取和回信幂等。执行器负责到期、恢复、资源上限和应用已确认计划；模型在相同 Agent 循环中按触发上下文判断是否值得说明、继续观察或给出回信。设备电量、失联、数据缺失和基线可比性来自确定性查询及计算。

现有 SQLite/Alembic 是上线基线，后台多进程并发行为尚需验证。单实例可以先采用数据库任务表和有界 worker；并发与锁竞争、延迟或恢复超过可接受范围时，再选择 PostgreSQL、独立队列或调度器。采用框架检查点仍需业务调度、交付与幂等。具体工作进程与数据库方案由 P13 定稿。

**定型门槛。** P13 用重复触发、worker 中止重启、外部超时、结果已写但未交付等故障验证恢复。P14 验证设备事件与周期回顾的触发和打扰区分。P15 在确认、暂停、到期与修订之间验证生效范围。P16 验证个人变化只基于真实就绪状态，重复回顾与委托可定位同一事实而各自保留来历。 [服务端数据库说明](../server/README.md) · [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

## 7. 状态传输、收件箱和推送 · P02、P05、P06、P17、P18

**首轮保留现有接口。** App 沿用 POST 创建回合与 GET 轮询状态。内部执行事件按已保存的回合、阶段和交付标识映射给客户端。回合成功或失败、断线重连及 App 重启都以持久状态为准。SSE 可在实时反馈成为实测瓶颈时评审；复用遥测 WebSocket 会耦合业务协议和恢复约定。P05/P06 先量化首字、完成速度、轮询负担和断线恢复。

收件箱通过持久记录定位主题、设备、记录范围或委托结果。原生推送沿用 Expo Notifications 与 Expo Push Service 的既有选型，P18 验证原生构建、权限、设备 token 与凭据。点击后按用户和设备鉴权定位，敏感正文在进入 App 后读取。

**定型门槛。** P17 验证重复交付去重、已读同步和多入口定位。P18 按目标平台验证后台到达、冷启动、换账号或 token 变更，以及无权限、丢送达或重复推送仍能通过收件箱查看。 [Expo SDK 58 Notifications](https://docs.expo.dev/versions/v58.0.0/sdk/notifications/)

## 8. 图片和联网知识 · P11、P12

**图片建议沿用现有模型适配。** P11 实测 MiniMax 多模态和当前账户，验收上传、格式与大小、同主题追问、压缩和失败。照片内容是当轮交流证据，持久化需绑定授权范围和业务用途。替换模型或启用额外图像提供商需用同样样本验证准确性、用量和隐私。

**搜索延续用户指定的 MiniMax 方向。** 以受控搜索和阅读工具接入。P12 核对目标模型、端点和账户的搜索与阅读能力、来源 URL、读取时间、额度、出网及使用条件。MiniMax 的套餐介绍能说明有搜索能力的入口，接入本项目的可用性以实测为准。如果当前接口无法支持稳定可核对的网页来源，再评审其他搜索提供商或分阶段上线。外部内容作为工具数据，保留与本宠观测不同的证据类型。

**定型门槛。** P11 在目标设备通过图片显示和权限清理。P12 完成真实搜索与页面阅读，覆盖来源冲突、访问失败、恶意网页指令、敏感字段出网与查询权限。 [MiniMax 模型调用](https://platform.minimax.io/docs/guides/text-generation) · [MiniMax Token Plan](https://platform.minimax.io/subscribe/token-plan)

## 9. 权限、审计、评测和发布 · P00、P05、P20

**权限与隐私为产品约束。** 模型、用户内容、网页和工具结果拥有各自的信任边界。模型输出允许提出操作；服务端按主体授权、运行环境、能力和绑定的确认版本执行。确认回执幂等并可授权复查。使用只读工具时限制出网和外部数据目的。模型凭据限服务端，日志、检查点和外部遥测采用最小数据与租户隔离。批准的写入和未批准的候选在产品记录中各自保留状态。

**推荐先用项目自身的结构化日志和验收集。** 记录运行触发、回合与工具调用标识、参数摘要、结果引用、耗时、预算、故障阶段、交付状态和版本。审计解释来自事实和结果事件。运行轨迹重建与重新执行分别验收，真实写操作只能依授权执行并用稳定键避免重复。外部托管日志、评测或运行平台需要明确数据边界后再评审。

**定型门槛。** P05 复跑已有 17 条生产验收场景，并补未见过的问法、多个时段、主题引用、外部内容注入、空窗口、无来源事实、角色、工具故障与越权。用实际工具、授权、回执及来源定位判分，结合耗时、调用数和费用比较现网基线。P20 验证真实产品 API 和设备可用性、兼容、迁移、配置回退及已有页面的交互回归。测试结论注明模型/依赖版本、数据、账号环境与客户端。 [G1 实施记录](./agent-phase-one.md) · [工作包验收](./agent-implementation-work-packages.md)
