# 伙伴群聊双 Agent 重构设计

状态：2026-11-24 定稿，D1–D3 经负责人确认。依据本地 main（c84e9f8）及既有契约。延迟和模型行为由本分支验收记录补充。

## 1. 目标与范围

一个群聊包含主人、爱宠 Agent 和照料助手 Agent。每条主人消息先经过意图判断，再交给被选中的一位或两位 Agent。两位分别运行，各有独立系统提示、上下文组装、工具权限、预算和轨迹，可共用模型与执行框架。两位看到同一群聊，按权限读取共享的已观测事实和记忆。每条发言的身份从创建起固定，流式、终态和重连回放用同一个消息 ID，来源和操作卡归到实际发言者。

这是对 V11 单 Agent 方案的变更。V10 也曾使用前置分类，当时会根据意图进入固定流程。本次路由负责收件人、分工和话题边界，接到消息的 Agent 自主决定查询、回答、提案或澄清。既有委托、提醒、回顾和收件箱继续进入同一群聊，首版由照料助手交付。

## 2. 交互决策

| 决策 | 推荐 | 其他选择与影响 |
| --- | --- | --- |
| D1 无点名时谁接话，已确认 | 默认一位，有不同内容时两位都答。例如爱宠表达感受，助手查活动记录 | 显式点名和引用的优先级按本稿建议处理，点名两位可双答 |
| D2 同轮两位怎样互动，已确认 | 第二位可以接第一位已经发出的消息补充一次。首版一轮至多每位各一条，互不依赖时可并行 | 并行仍使用持久化顺序和固定身份。只有主人的新消息开启下一轮 |
| D3 点名爱宠但请求查证或操作，已确认 | 爱宠先接话，照料助手查证或操作并署名 | 首版权限按本稿建议，爱宠只读基础事实和共享记忆，助手负责详细查询、联网、业务写入和动作，沿用原有明确指令与确认条件 |

首版沿用现有助手设定，服务端分别维护两位的默认表达。若要在 App 中自由配置两位人格，单独确认开放字段和作用范围。工具与事实边界由服务端维护。

按推荐项举例，「想我了吗？」由爱宠答。「它今天走了多久？」由助手查记录后答。「你今天玩得开心吗？也帮我查一下走了多久」可以让爱宠接话、助手另发一条带来源的回答。追问助手那一条时，用被引用消息确定对象，即使它是同一轮的第二条。

### 2.1 两位的内容分工

- **爱宠提供陪伴。** 用宠物第一人称，适合打招呼、撒娇、情绪回应、和主人聊简单的共同经历。通常一到两句，不报健康、活动、位置或设备数据，不做诊断、分析或承诺操作；不把拟人身份编成真实观测。首版仅允许读取需要的基础档案和共享记忆，可优先使用现有共享上下文。点名爱宠要求查证时，它只接住主人的话并把事实部分交给助手。
- **照料助手给专业结果。** 负责观测事实、养宠知识、判断依据及操作结果。首句直接回答，按现有简洁或详细设置展开。涉及时间范围、有效覆盖、来源或明确的不确定性时照常交代。双答时只回答本轮明确请求的专业部分。即使陪伴语句中的行为也能引出养宠建议，主人没问就省略。
- **双答要有两份不同的任务。** 路由输出使用可校验的分类与分工，服务端为两位生成各自任务。禁止把同一个专业问题作为两位的共同回答任务。点名两位但实际只有专业问题时，爱宠至多给一句陪伴式承接，事实由助手独占；普通闲聊无需助手凑话。权限由代码检查，不能只写在提示词里。

## 3. 路由与执行

1. 按宠物与请求键接收并去重主人消息。新客户端收到接受回执后对账本地气泡，从 WS 或轮询获取回复。持久化队列复用现有作业框架，先验证聊天时效、并发和重启恢复。
2. 路由器读取显式点名、被引用消息的实际发言人、本轮消息和近期主题上下文，输出范围、意图、拟发言者、顺序、依赖和简短理由。服务器校验枚举与组合，并落实点名及权限约束。路由器没有工具，也不发言。首版路由仅看附图数量，接收者按现有附件鉴权读取图片。路由异常时，由被点名者（未点名时由助手）发出有限澄清，范围未确认时不挂工具。
3. 按持久化路由结果分别建立运行与消息。独立发言可并行，需要回应前一位时等其消息提交。只有主人的新消息启动新一轮路由。每位有独立状态、超时和工具预算，并受整轮时间与调用预算约束。
4. 工具声明和执行都检查角色、运行形态、话题范围、主体归属与确认条件。只在路由判定允许后给照料助手挂供应商联网搜索。写入依据仍是主人原始指令或已有确认协议，另一位 Agent 的发言不能作为授权。复用并核对现有动作幂等，防止重试重复执行。
5. 服务端按分配角色生成消息身份，不从模型正文识别角色标记。路由记录与每位的轨迹共享回合 ID，可以追溯谁被选中、由谁调工具及结果进入了哪条消息。

实现中，路由器可为可拆分的混合请求逐字摘录两段原话。服务端校验原文位置、无重叠，以及剩余文字仅为标点、衔接或句首称呼后，将两段分别交给两位。无法无损拆分时保留完整请求和各自任务限制。纯专业请求里的爱宠转接只提供通用任务，模型从服务端允许的短句中选择，任何其他候选在上屏前替换为允许的短句。其他爱宠发言在流式和终态共用一段、至多两句的正文限制。首版按持久化顺序调度一轮的两条消息，承接时可读前一条已提交正文。

## 4. 持久化与 App 协议

保留 AgentTurn 作为主人来信、请求去重和主题锚点，新增按回合归属的回复记录，保存稳定消息 ID、角色、顺序、状态、正文、来源和内容块。首版用回合 ID 与角色限制每位各一条。每个 AgentRun 关联所属消息，路由结果持久化，重试沿用同一份分发结果。

新增消息级引用并校验归属，继续识别旧的回合级引用。当前客户端发言对象是单选，新协议支持显式选择两位。历史回合可用已有正文块投影成稳定的只读消息 ID，无块记录按既有发言人字段回退。主题、收件箱、历史确认卡继续锚定原 ID。

WS 增量和轮询快照均按消息 ID 更新，附累计正文及单调版本。客户端忽略过时帧，同一发言从首字到完成保留同一个气泡。每条回复状态独立，允许一位成功、另一位失败。重试只处理失败的运行且保留成功消息。业务动作已生效或状态未知时先检查持久结果，不能确定时如实说明，避免自动重放副作用。

新协议由客户端声明，默认启用。老客户端继续使用现有协议，读取双 Agent 已交付的历史时由服务端投影成旧回合结构。回退时停止让新消息进入双 Agent，已入队的回合按持久化计划收尾，已生成的历史继续可读。

## 5. 工作量和实施顺序

复杂度中高。估算假设复用现有模型适配器、工具注册表、后台交付和 App 会话容器，首版每位每轮最多发一条。单人约 **8–12 个工程日**做到可发布。

| 工作 | 工程日 | 交付 |
| --- | --- | --- |
| 路由和双角色运行 | 2–3 | 角色提示、权限、独立运行和可回放记录，先验证纯文本与明确点名 |
| 消息、队列及协议 | 2–3 | 独立持久化消息、幂等、部分失败、历史投影、WS 和轮询 |
| App 接入 | 2–3 | 逐条显示、引用、角色状态和来源卡归属，增量到终态保持身份 |
| 回归和发布 | 2–3 | 行为评测、新旧协议、重启恢复、iOS 功能与视觉验收 |

纯聊天通常由一次调用变为路由加一次回答。双答通常是一次路由加两次回答，工具多轮另计。路由增加首字前的等待，串行补充还会推迟第二条。用同一组样本对照现有链路，分别测首条正文首字、两条完成时间、路由耗时及模型用量。主要不确定性是含混追问的路由质量、双答是否重复，以及部分失败时业务动作能否安全恢复。

## 6. 验收

- 覆盖无点名、分别点名、双点名、精确引用第二条消息、简短追问、图片、混合意图、范围外和路由异常。连续至少八轮检查双答是否互补。
- 两个专项回归。点名爱宠询问专业问题时，即使路由模型给了相反的发言顺序，爱宠仍须先接话。对「栗子，我想抱抱你。顺便帮我查一下今天有多少活动记录」，爱宠接住抱抱，助手只回答活动记录及其数据边界，省略抱猫建议。这两项由编码前段的真实模型试跑及确定性路由探针发现，须在最终候选上复验。
- 隔离真模型曾在纯专业请求的爱宠消息内冒充助手，继续输出饮食建议。在「只承接」的计划中，爱宠必须使用服务端约束的短承接，不把专业请求交给它生成。其他爱宠发言也应在上屏前限制表达长度并去掉模型自己追加的异角色发言段。
- 路由器调用异常和回复为空或不可解析要落完整降级记录，并完成有限澄清。隔离真实模型试跑曾触发无来源字段的降级计划，导致回合悬挂，须覆盖从路由返回到终态的完整路径。
- WS 分帧需覆盖同一次数据库快照之间的多条增量。隔离探针收到过共享同一版本的多个不同正文，须验证每段既能追加，也不会被晚到的较旧版本覆盖。若使用独立的帧序号，应与消息尝试版本一起校验重试和断线恢复。
- 单答、双答、第二位慢或失败、断线重连、轮询恢复、重复提交，以及服务重启后恢复。检查头像不跳变、正文和来源不串、独立重试不会重复消息或动作。
- 回归确认卡、委托、设备动作、联网来源、后台回信、收件箱深链、旧历史和账号隔离。
- iOS 功能与截图视觉分开走查。浅色与深色分别核对发言身份、双答布局、等待失败状态、来源卡、键盘和上翻历史时的滚动位置。

## 7. 合并门槛

- ZCode CLI 使用 GLM-5.4 在功能分支实施，按实际交付同步产品设计、P00 契约及项目入口。该模型指定用于编码，产品内对话模型依现有服务配置。
- 跑服务端 unittest、客户端 lint/typecheck/format/test、Web 构建。覆盖 SQLite 迁移前后、旧客户端与新协议、旧历史、断线和恢复。对照可控分段输出验证首帧身份、后续消息稳定、重复/乱序帧、第二位失败，以及正文中普通角色称谓。
- Codex 独立在 iOS 模拟器验收通过后才能合并 main。用隔离服务验证本分支 App 和服务端；真实模型验证分工和回答，分段夹具覆盖确定的断线、失败和乱序，记录数据来源、设备、环境和场景，分开记实证与未验证项。实际检查气泡排版和顺序，用截图保存证据。
