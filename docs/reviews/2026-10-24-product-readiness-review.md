# PetSense：个人用户多租户产品审查与改造路线

审查日期：2026-10-24。代码基线：`8ee8d47d3d3c5632793885d7daade6568ead0ece`。

产品边界已由用户确认：**每个用户独立拥有宠物和设备，暂不共享宠物**。
首期不引入组织、门店、家庭成员、复杂 RBAC，也不要求每用户一套数据库。

## 1. 总体判断

项目已有真实遥测、账号、社区、AI 代理、采集存储和自动部署基础，可以逐步改造。
但目前不能按成熟的多用户健康管理产品对外开放。主要障碍是：

1. 认证覆盖不完整，设备没有可验证的所有权，私有数据和控制能力可跨用户访问。
2. 数据模型及客户端状态仍围绕一台演示设备，全局缓存、全局告警与硬编码路由会串数据。
3. 活动时长和趋势存在确定的计算错误，部分界面展示仍混入模拟位置和无来源的日记数字。
4. 宠物、设备、生成任务和账号切换的完整生命周期尚未实现。
5. 当前单进程、线程共享 cursor、同步外部任务和本机文件存储，缺少扩容及故障恢复边界。

不建议先重做全部 UI、直接换框架或上 Kubernetes。建议保留 Expo/React Native 和 Flask，
先完成个人用户的数据隔离，再建立清晰模块、数据库迁移和异步处理。

## 2. 范围、证据与限制

已阅读所有页面业务逻辑，相关组件、Hook、客户端服务；后端账号/宠物/社区/趋势/AI/
采集接口；遥测、告警、分类器；固件关键采集与通信路径；CI 和部署代码。
审查分三个独立只读方向完成后交叉核验，没有修改业务代码、部署服务或发送线上设备命令。

本轮重新验证：lint、typecheck、format:check、遥测四组自检、11 项 Python 测试均通过。
这些检查主要覆盖代码质量、解析器、规则逻辑及部署安全路径，未覆盖多用户隔离与完整交互。

关键问题另外使用 AST 提取真实函数、内存 SQLite 或隔离执行验证，没有运行生产入口：

- 实际 1 秒、10Hz 的活动数据，写出 `active_seconds=5000`，页面统计返回 83 分钟。
- 当天两个小时心率分别 100、200，日趋势回退只保留首小时，结果为 100。
- 共享 cursor 的查询在 fetch 前被另一查询覆盖，首次调用方读到后一次结果。
- 五台不同设备各一帧高心率，会累计触发同一个客户端告警。
- 10Hz 下 sensorOff 约 8.9 秒触发，而配置注释按约三分钟设计。

未逐一进行 iOS/Android 真机、浏览器布局及真实弱网交互测试；权限弹窗、跨平台 Share/
Alert 表现等不写成已复现缺陷。单进程部署下尚未实际发生的多 worker 风险另行注明。
下述源码位置均相对仓库根目录，行号对应上述代码基线。

## 3. 优先级定义

| 级别 | 含义                                                            | 推进要求                 |
| ---- | --------------------------------------------------------------- | ------------------------ |
| P0   | 未授权访问、跨用户私有数据/设备控制、公共付费代理或认证传输风险 | 接入不可信多用户之前完成 |
| P1   | 核心结果错误、流程失败、状态串用、数据丢失或稳定性设计阻断      | 稳定内测之前完成         |
| P2   | 完整产品体验、规模化运营和交付能力缺口                          | 正式发布前按路线补齐     |

优先级依据产品影响，不是声称每项已经在线上被利用。
公开社区本身不是越权；需要隔离的是私有健康、位置、设备、采集及未公开生成资产。

## 4. P0：先封住数据与控制边界

### P0-01：匿名遥测及控制入口没有接入账号权限

**证据：** `server/server.py:1302` 的 `/ws` 直接加入全局广播；`:1311` 原始帧查询、
`:1352` 动作查询、`:1371` 录音控制、`:1442` 实验控制没有账号鉴权。
`:2407` 趋势和 `:2429` UWB 快照同样无鉴权；趋势读取全局实验，位置保存为全局单帧。

**影响：** 网络可访问这些入口的人可以读取私有遥测，部分接口还能控制固定设备。
前端隐藏入口不能修复服务端权限；WebSocket 加一个 deviceId 参数也不能充当授权。

**改造：** 默认拒绝私有接口；会话认证后每次校验设备所有权；研究/运维控制单独保护，
不直接暴露给普通 App 用户。订阅只返回有权访问的设备，退出和会话撤销后断开对应连接。

**验收：** 匿名 401；B 请求 A 的设备统一拒绝；更换参数、深链接、WebSocket 重新订阅及
已注销 token 都不能绕过；测试禁止真实设备执行命令。

### P0-02：任意设备 ID 可被任何账号“认领”

**证据：** `server/server.py:1915` 接收任意 deviceId，`:1922` 直接保存；无设备注册、
配对证明和有效绑定唯一约束。`:2584` 的公开用户资料还返回 device_id 和后续在线信息。
`:1987` 按填入的 ID 读取健康快照。

**影响：** B 知道或猜到 A 的设备 ID 后，创建自己的宠物绑定它，即可经自己的看板读取
A 的数据。`:1138` 又把重复绑定设备的统计只记到第一只宠物。

**改造：** 独立设备表、一次性配对凭证、原子认领和唯一有效绑定；公开资料不返回设备标识、
电量与在线信息。设备转移保留历史绑定区间，不能把旧主人的历史健康记录交给新主人。

**验收：** 并发抢绑只能成功一次；B 不能凭裸 ID 绑定 A 的设备；解绑/转移有确认与审计；
新主人看不到转移前的私有数据。

### P0-03：AI 代理对匿名用户开放，第三方对象没有本地所有权

**证据：** `server/server.py:2087`、`:2095`、`:2112`、`:2161`、`:2275` 的形象读取、
生成、日记、户型代理没有 require_app_user，调用的是共享上游 API key。
`:1960` 允许给自己的宠物绑定任意 petgifId，没有 provider asset 所有者记录。

**影响：** 匿名调用可消耗上游额度；知道别人的 provider ID 即可跨对象读取或发起操作。
具体是否产生账单及能否覆盖上游文件取决于上游，但本地越权调用边界已确定缺失。

**改造：** 所有上游请求通过本地 owner-scoped job/asset 映射；不接受任意 provider ID；
所有生成鉴权、限流、并发限制与个人配额，重复提交具备幂等键。

**验收：** 匿名或 B 操作 A 的任务/资产时，上游 mock 调用次数必须为零。

### P0-04：线上 HTTP/WS 传输会话与私有内容

**证据：** `src/config.ts:16` 默认 ws，`:22` REST 为 http；`app.json` 设置
NSAllowsArbitraryLoads。已知线上入口亦使用 HTTP。

**影响：** 登录密码、会话 token 和健康数据缺少传输加密保护。换数据库或 TAT 不能解决。

**改造：** 域名与 TLS，统一 HTTPS/WSS 配置，确认反代 WebSocket/上传超时，再移除明文豁免。
登录、注册、找回与高成本接口限流；保留现有随机 token、服务端哈希和有效期基础。

**验收：** 发布构建没有生产 HTTP/WS URL；证书续期、WebSocket、媒体及真机上传均通过。

## 5. P1：数据正确性、设备链路和运行稳定性

### P1-01：设备身份与路由写死，当前单设备也有两套 ID

**证据：** `firmware/petsense_esp32/board_config.h:60` 附近，topic/client 为 esp32-001，
payload ID 为 petsense-esp32-001。`server/server.py:1191` 用宠物 device_id 拼 topic，
`:1138` 统计用 payload ID，首页 `src/app/(tabs)/index.tsx:134` 也匹配 payload ID。
服务端 `:916`、`:939`、`:945` 只对固定 topic 展开批次、推断和更新统计。

**结果：** 填短 ID 快照可能正常、实时匹配及统计失败；填长 ID 则反过来。第二台设备的批次
不会获得与第一台相同的处理。单纯把一个字符串替换掉不能迁移所有历史引用。

**改造/验收：** 建规范设备主键及旧 ID/topic 别名映射；客户端使用主键；传输层凭证绑定身份；
所有已注册设备走通用路由。两台不同 ID 同时上报，四类数据均更新，旧设备仍兼容。

### P1-02：时长单位错误，不能只修 UI 除数

**证据：** `server/server.py:1157` 的毫秒间隔被至少放大到 500ms，`:1165` 起写入
sleep_seconds/active_seconds，`:1232` 又除 60 当作秒转分钟。

**结果：** 正常 1Hz 就放大约千倍；10Hz 再被最小间隔放大五倍。

**改造/验收：** 单位写入字段/契约；按有效设备时间差累加，考虑 boot、seq、乱序、重发和
断流上限。相同 60 秒行为在 1Hz/10Hz 都等于 60 秒，重复帧不增加。原始数据仍在时重算；
无法重算的历史统计标为不可用，不应未经验证全部除 1000。

### P1-03：趋势来源、覆盖范围和统计口径均有问题

- `server/server.py:2301` 遍历所有实验；`:2373` 日趋势固定设备；`:2407` 不接收宠物归属。
- `:2361` 仅在当天桶 samples=0 时合并，第一非空小时之后其余小时都被忽略；CSV 若已有
  一点数据，当天新实时值也不再合入。
- `src/services/api.ts:228` 只传 period；首页 `:110` 的 effect 不依赖 petId，切宠不刷新趋势。
- 首页 `:216` 对桶平均值再等权平均，并用均值求最低/最高，不是原始样本的全期统计。
- 后端 samples 是不同指标数量之和，不能直接当每种指标的权重；需要各指标 count/sum。

**改造：** owner/pet/device/time 范围契约；后端返回每指标 count/sum/min/max、coverage 与
缺失区间；研究数据显式回放，不混进用户历史；CSV/实时去重后聚合。前端只展示该 summary，
按用户、宠物、周期请求并刷新。

**验收：** A/B 历史不同、样本量不等、缺指标、跨日、重复来源、多小时输入均对齐独立基准计算；
数据不足不能显示成完整全天健康结论。

### P1-04：10,000 条全局缓冲不是健康历史库

**证据：** `server/server.py:35`、`:296` 全 topic 共用 MAX_HISTORY=10000 并删除旧行；
`:2368` 的24小时趋势依赖这张 readings。单设备10Hz便仅约16.7分钟，其他设备/音频会再挤占。

**改造/验收：** 业务历史与瞬时缓冲分开；按设备时间保留原始记录和分钟/小时汇总，原始大批次
按策略归档。输入超过10,000条的多设备24小时数据，仍能得到完整且有 coverage 的趋势。

### P1-05：客户端单例混设备，切账号与切宠物存在旧响应覆盖

**证据：** `src/hooks/use-telemetry.ts:45` 接收所有设备，设备切换就重置序列；
`src/hooks/use-alerts.ts:24` 共用一个引擎；首页 `:135` 的 liveForPet ?? latest
让其他设备驱动当前宠物动作。首页 `:80`、`:288` 及 profile `:29` 的请求无身份代次保护。

**结果：** B 帧改变 A 动作和警示；A 的慢请求可在登录 B 后覆盖界面；快速切宠响应顺序反转。

**改造/验收：** 会话范围 store；查询键包含 userId/petId/deviceId；旧请求 abort/代次校验；
退出先清私有缓存和连接。两账号交错帧、慢请求、切换过程中断网，都不得显示对方数据。

### P1-06：连接新鲜不等于传感器数据新鲜

**证据：** 首页 `src/app/(tabs)/index.tsx:138` 在断流后可一直回退到旧 dashboard.online，
体征也保留旧快照；固件 `.ino:3254` 附近更新 health 缓存后没有 UART 超时清 valid，
`:1335` 附近继续发送旧值。`action_classifier.py:139` 在输入无效或时钟回退时可返回旧预测，
`use-pet-action.ts:65` 不检查预测年龄和设备是否一致。

**改造/验收：** 分别记录 networkReceivedAt、sensorSampleAt、predictionWindow/boot；对每指标
独立判过期，显示最后测量时间及未知态。拔掉健康模块但保留 IMU/MQTT，体征必须失效；设备
重启不能继续沿用旧奔跑状态；断流不能永久显示在线。

### P1-07：告警按帧数去抖，只有 App 打开时才运行

**证据：** `src/constants/alerts.ts:21`、`:57`、`:135` 按约2秒一帧估算；
`src/services/alert-engine.ts:41` 对每帧计数，但固件现为100ms样本/每批最多十条。
`src/hooks/use-alerts.ts` 首个订阅者挂载才运行，全卸载即停止，没有服务端告警事件与通知投递。

**改造：** 以独立传感器样本及持续时间去抖，不因重传或批次切分改变；每设备状态机。
稳定产品的健康告警由服务端持久化并投递，App 展示/确认事件，增加冷却、恢复和静默策略。
阈值要按物种/设备可测能力验证，不能把统一阈值包装成医学诊断。

**验收：** 同一数据不同采样频率/重传/批次得到相同告警；B不能确认A告警；App关闭后仍有
告警记录和按设置投递。推送不是送达保证，需要区分已生成、已投递、已读。

### P1-08：Collection 的单一 bearer 不支持普通用户隔离

**证据：** `server/collection_api.py:38` 的会话/视频/帧没有 owner；`:169` 只比较一个
全局 token。`:118` 与`:134` 接受包体 device 和任意 session_id，没有核对会话所属设备。
`:244` quality 和`:391` alignment 的查询没有补齐设备边界。

**边界：** 当前不是匿名可访问漏洞；问题发生在把这个运营 bearer 直接交给普通用户时。
若采集系统仅内部研究使用，可以先独立放到受保护的运营入口。

**改造/验收：** 用户功能用个人会话，session/video/job 继承 owner，帧归属于已认证设备与
合法 session。B设备伪造 A会话时拒绝落库和 ACK；用户交叉 control/upload/finish/alignment
均拒绝。保留现有提交后ACK、CRC和重传幂等能力。

### P1-09：共享 cursor、慢连接和直接加 worker 都会破坏稳定性

**证据：** `server/server.py:87` 一个全局 cursor 同时供 MQTT 和 threaded HTTP 使用；
`:933`、`:971` 在 MQTT 回调线程逐个同步 socket.send，慢连接可拖住全部设备。
`:843` 固定 MQTT client_id，`:977` 起在模块导入时连接；`:2661` 线上入口使用 Werkzeug。

**改造：** 每操作独立数据库会话；单独 MQTT collector 负责验证、持久化、分发；WebSocket
每连接有界队列，落后连接断开/降采样。HTTP 使用生产服务器，但必须先移除导入即启动 MQTT。

**重要：** 目前是单进程 threaded，不能声称已经多 worker 重复采集；但直接启动多个 worker
会建立相同 client ID 的连接，且缓存、WS集合、位置、实验状态各自不一致。

**验收：** 持续写入时并发查询无串结果；一个停止读取的客户端不拖慢正常用户；重启 collector
能恢复，HTTP worker扩到2个时不新增MQTT消费者。生产服务器选型须核实 WebSocket 支持。

### P1-10：上传和文件处理没有完整资源上限

**证据：** `server/server.py:1261` 先 read 全文件才检查10MB；Collection `:333` 先读取
全部body才检查4MB；没有统一 MAX_CONTENT_LENGTH。`:1939` 下载/写入头像在归属检查之前，
`:2254` 等远程媒体下载无字节上限。媒体上传锁仅进程内，扩多进程后同offset可并发追加。

**改造/验收：** 网关与应用双层上限、流式有界读取、解码尺寸校验、先owner后下载；每用户
配额；上传临时对象与完成状态分开，失败清理。超限body有界拒绝，不存在pet不触发下载，
同一分块并发/重试不损坏文件。COS不自动解决授权、配额及上传状态机。

## 7. 推荐目标架构

### 7.1 先比较选择

| 路线                                               | 优点                                       | 主要代价                                  | 建议           |
| -------------------------------------------------- | ------------------------------------------ | ----------------------------------------- | -------------- |
| 继续SQLite并补owner/锁                             | 过渡改动小，可快速封边界                   | 时间序列增长、并发写、备份与多进程仍受限  | 只作为P0过渡   |
| 模块化Flask + PostgreSQL + 独立采集/任务进程 + COS | 保留现有能力，逐步迁移，权限和运行边界清楚 | 需要迁移、对象存储配置与运维              | 推荐首个稳定版 |
| 全量重写/微服务/Kubernetes                         | 可重做所有接口和运行方式                   | 同时改变过多变量，现有业务bug仍须逐一解决 | 暂不采用       |

结构建议：

```text
Expo App / Web
    ├─ HTTPS API：认证、owner权限、宠物、设备、社区、任务查询
    └─ WSS：短期订阅凭证，服务端校验设备归属

设备 ── 每设备凭证/TLS MQTT ── 独立collector
                                ├─ 规范化、去重、落库
                                ├─ 按设备分发到WS
                                └─ 统计/告警处理

API ── PostgreSQL：业务记录、任务状态、遥测元数据/近期时间序列
    ├─ 有界任务队列/worker：AI、转码、导出、通知
    └─ COS：照片、视频、原始批次归档、模型、发布包
```

进程拆开是运行边界，不要求拆成多个独立仓库或复杂微服务。Redis等中间件只有在承担明确的
队列、跨进程分发或缓存职责时引入；任务最终状态和幂等信息仍要持久保存。

### 7.2 个人用户即租户的数据模型

- `users`：账号状态、认证信息；保留已存在的密码哈希基础，不回退明文或可逆存储。
- `pets(id, owner_user_id, ...)`：统一私有归属，提供编辑、归档/删除行为。
- `devices(id, owner_user_id, serial, status, ...)`：规范主键和配对状态；传输别名独立表。
- `device_bindings(device_id, pet_id, owner_user_id, valid_from, valid_to)`：有效绑定约束与历史。
- `telemetry_events(owner_user_id, device_id, binding_id, boot_id, seq, sampled_at, received_at, ...)`：
  采集时归属、来源和唯一事件身份；各传感器保留独立采样时间。
- `metric_rollups`：按设备、时间桶和指标记录 sum/count/min/max/coverage，避免对均值再平均。
- `alert_events` / `notification_deliveries`：告警发生、恢复、确认、投递结果分开。
- `generation_jobs` / `provider_assets`：owner、pet、幂等键、provider_id、状态、重试与配额。
- `collection_sessions` / `videos` / `uploads`：owner从父资源继承，不接受客户端自填owner。
- 社区 `posts` 明确visibility；公开的是用户选择发布的内容，不是整份健康档案和原始资产。

所有私有查询从当前认证用户出发；path里的petId/deviceId、缓存命中和后台worker同样校验。
数据库外键/复合约束防止把A的设备绑定B的宠物。PostgreSQL RLS可以再加一层防御，但不能
替代业务授权；若使用，连接用户不能是绕过RLS的超级用户，连接池上下文应按事务设置/清除。

### 7.3 存储与量级

不建议每用户一库。首期共享PostgreSQL、按owner隔离，私有COS对象按owner/resource分类，
下载由服务端授权后发短期URL；对象前缀和不可猜文件名不是权限机制。

10Hz意味着**每设备每天864,000帧**；100台就是每天86,400,000帧。这是容量换算，不是已确认
的产品负载目标。因此需要定义哪些原始数据保留、哪些降采样/聚合、哪些仅实验时采集；不能
把所有完整帧永久塞进业务表。对象归档格式、分区及保留期限按真实负载测试决定。

## 8. 分阶段实施方案与验收门槛

### 阶段0：生产封边界与备份，P0

**交付：** 列出全部路由的公开/私有/运营权限矩阵；关闭匿名私有数据和控制；AI代理鉴权及
临时限额；阻止裸ID重复认领；TLS；自动备份与一次实际恢复演练。

**文件范围：** server.py路由与认证、collection_api入口、src/config.ts、反代/部署配置。
过渡期间运营采集与普通用户入口分开，不把全局采集token分发给App。

**门槛：** A/B/匿名三类测试完整通过；恢复到隔离环境可核对账号、宠物、帧、媒体引用。
尚不满足前，不进入外部多用户试用。

### 阶段1：设备与owner贯通，P0/P1

**交付：** devices及别名、验证配对、解绑转移、有效绑定约束；REST/WS/趋势/位置/任务/媒体
完整owner链；客户端统一activePet和身份范围store；移除任意设备兜底与演示默认数据。

**结构：** server包按auth/pets/devices/telemetry/collection/social/generation划模块，使用
应用工厂，导入不连接MQTT；先不改变已验证的业务行为，再逐项替换查询。

**门槛：** 两用户、每人两宠物、三台设备、交错上报/切账号/转移/伪造ID，所有输出和副作用
均符合权限矩阵；第二台设备获得与第一台相同的完整链路。

### 阶段2：正确统计、可靠采集与数据库迁移，P1

**交付：** 明确单位与新鲜度契约；修统计/趋势/告警去抖；独立collector与有界分发；
迁移到PostgreSQL和版本化schema；建立近期事件、聚合、归档的保留策略。

**迁移顺序：** 备份 → 盘点重复设备/孤儿/来源不明数据 → 加可空新字段 → 回填与核对 →
对照读验证 → 切读写 → 加非空/FK/唯一约束 → 观察后移除旧路径。
历史owner无法证明的实验/采集记录隔离保留，不默认交给第一个用户。

**门槛：** 1Hz/10Hz、重放、乱序、重启、断流、跨日、设备转移结果可重复；新旧数据数量、
时间范围与抽样内容核对；并发写读不串查询；备份恢复和向前兼容回滚演练通过。

### 阶段3：核心交互闭环与后台任务，P1

**交付：** 宠物/设备管理、正确添加入口、AI角色卡可用；AI/日记/上传持久任务与幂等；
页面错误/空态/取消/恢复；真实定位或明确的无定位态；日记来源与关联正确。
修评论重复、关注状态和跨域删除，补齐个人资料与账号会话管理。

**门槛：** 新账号注册→建宠→配对→看体征/趋势→AI→发帖→评论→退出/重登的跨端E2E；
在每一步注入断网、401、500、请求超时和组件卸载，数据不重复、不串账号、结果可恢复。

### 阶段4：可运营、可恢复、可持续交付，P2

**交付：** COS私有媒体与配额；服务端告警事件和通知投递；真实举报处理；社区分页搜索；
结构化日志/requestId、错误追踪、指标、staging、数据库迁移发布检查及运行手册。

CI保留现有检查，加入遥测自检、owner权限矩阵、契约/E2E和故障测试。
部署可演进到GitHub Actions + COS + TAT：模型按哈希复用、依赖按锁文件复用，避免每次传29MB。
TAT agent服务已安装且为active，API在线状态仍需核验；项目的COS接入和有效腾讯云API凭据尚未配置完成，不能视为已落地。

**门槛：** 分级负载测试、慢客户端、collector/worker/数据库/上游AI故障演练、备份恢复，
达到事先约定的容量及服务目标后再正式发布。

## 9. 必须纳入测试的场景

1. **权限矩阵：** 匿名/A/B × 所有私有资源的读、写、列表、导出、订阅、缓存命中。
2. **设备生命周期：** 并发认领、凭证错误、解绑、转移、重启、旧ID兼容和历史数据归属。
3. **真实性：** 无设备不生成位置，未知步数不变8000，0不变30，过期体征不显示实时健康。
4. **时间口径：** 单位、采样频率、缺失、乱序、boot/seq、重复、跨日与时间偏差。
5. **业务幂等：** 建宠、AI、发帖、评论、点赞、关注、分块上传，重试不能产生重复副作用。
6. **客户端竞态：** A慢请求后切B、快速切宠、页面卸载、返回栈、失效会话及本地存储失败。
7. **稳定性：** 一个慢WS、上游超时、磁盘满、队列积压、数据库中断不应拖垮所有用户。
8. **交付恢复：** 发布前后schema兼容；代码回滚不当作数据库回滚；恢复后私有媒体引用仍正确。

初始压测建议按1/10/50台模拟设备分档，在真实采样频率下测试，再根据产品目标扩展。
记录吞吐、积压、丢帧/重复、端到端延迟、P95 API延迟、数据库增长及每用户AI成本。
性能数字和RPO/RTO须在阶段0确定验收目标，本报告不把未经测试的吞吐或工期作为承诺。

## 10. 已有能力应保留，以及尚待产品决定的内容

应保留：随机会话token及哈希、PBKDF2密码校验、部分宠物归属检查、跨端上传封装、
解析数值校验、无效健康帧不进曲线、自动重连、分类器按设备窗口、Collection落库后ACK、
现有CI和代码/解释器回滚。应在它们上面补齐边界，而不是全部推倒。

待决定但不阻断本轮结论：用户规模与设备频率、历史保留期、是否把研究采集向普通用户开放、
社区默认公开范围、AI成本/额度、通知渠道、实际可承诺的定位能力、备份RPO/RTO和发布标准。

建议实施顺序：**P0边界 → owner/设备全链路 → 统计与可靠采集 → 核心交互与异步任务 →
存储/交付/运营完善**。数据库迁移和交互修复可按依赖拆分，但不应先扩用户再补隔离。
