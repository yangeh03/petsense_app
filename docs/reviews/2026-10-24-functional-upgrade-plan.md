# PetSense 功能与稳定性升级方案

日期：2026-10-24。基于同日代码审查，基线 `8ee8d47`。

本版按用户要求，不讨论鉴权、越权、加密、隐私、攻击防护等问题。
用户模型保持“每个用户独立拥有宠物，暂不共享”。多用户数据关联只从功能正确性评估：
界面必须显示当前账号、当前宠物、当前设备的数据，不能错配或沿用旧结果。

## 1. 结论与优先级

当前最需要解决的是三件事：**数据算得对、核心流程能完成、多设备运行不互相干扰**。
先换数据库、换UI或优化部署，均不能替代这些修复。

| 级别 | 定义                                                      |
| ---- | --------------------------------------------------------- |
| P0   | 当前核心结果明显错误或核心功能无法完成，先修              |
| P1   | 多用户/多设备、重试、断网和并发场景不可靠，稳定内测前完成 |
| P2   | 产品生命周期、体验一致性和交付效率不足，正式产品阶段补齐  |

本版P0是功能优先级，不沿用上一版的安全风险含义。

## 2. P0：首先修复的核心功能

### F01：运动与睡眠统计严重错误

- 位置：`server/server.py:1157`、`:1165`、`:1232`。
- 毫秒间隔写入名为seconds的字段，再除60显示分钟；100ms间隔又被至少放大到500ms。
- 已隔离验证：实际1秒、10Hz活动被显示为83分钟。
- 改造：明确统一单位，使用真实有效采样间隔；去重、重启、乱序和断流不能虚增时长。
- 验收：1Hz和10Hz的同一60秒行为均得到60秒；累计不能超过实际观测覆盖时间。
- 历史：有原始数据则重算；不能把所有旧值简单除1000，因为不同采样率放大倍数不同。

### F02：设备标识不统一，第二台设备不能完整工作

- 位置：固件`board_config.h:60`附近；`server.py:916`、`:939`、`:945`、`:1138`、`:1191`；
  `src/app/(tabs)/index.tsx:134`。
- topic/client使用esp32-001，payload使用petsense-esp32-001；快照、统计、实时匹配查找方式不同。
- 服务端只对写死的首台设备展开批次、推断动作、更新统计和位置。
- 改造：独立设备实体，统一内部deviceId，保留旧ID和topic映射；通用处理所有注册设备。
- 验收：至少两台设备交错上报，各自快照、体征、动作、趋势和统计完整更新。

### F03：趋势既不跟随宠物，也不是正确的全期统计

- 位置：`server.py:2301`、`:2361`、`:2373`；`src/services/api.ts:228`；首页`:110`、`:216`。
- 后端使用全局实验数据和固定设备；前端切宠物不重取趋势，下拉也不统一刷新。
- 当天统计只合入首个非空小时；前端把各桶均值等权平均，并把桶均值的极值当全期极值。
- 改造：趋势契约包含petId/deviceId/timeRange；后端返回每指标count/sum/min/max、数据覆盖率；
  前端展示后端summary，查询键包含当前用户、宠物、周期。
- 验收：两宠物历史不同；不同小时/不同样本数、缺失指标、重叠来源的结果与独立基准一致。

### F04：已有宠物的AI角色卡入口实际不可用

- 位置：`src/components/dashboard/character-card-modal.tsx:153`。
- 唯一选图按钮被false &&隐藏，生成按钮又要求已有图片。返回202后也没有实际状态恢复轮询。
- 改造：恢复选图→生成→预览→应用链路，明确处理中、失败、超时；任务结果可重新打开查看。
- 验收：已有宠物从入口完成整条流程；同步成功、202后成功、失败和关闭重开均有正确终态。

### F05：位置和日记仍包含演示级内容

- 位置：`tracking.tsx:33`、`:157`；`floor-plan.tsx:31`；`diary-modal.tsx:46`、`:78`。
- 位置使用固定户型、路线和宠物图标，真实UWB Hook没有接入；主状态仍称实时。
- 日记默认8000步，并把真实0分钟替换成30分钟，缺数字形象时用default回退。
- 改造：明确真实数据、手动填写、演示三种来源；无定位就显示无定位；未知步数保持未知。
- 验收：设备静止/离线时不能自行巡游；0不变30；生成和发布的文字、数字、宠物关联一致。
- 决策：没有可用定位硬件时，可以暂缓真实定位功能，但不能把动画当成已完成定位。

## 3. P1：稳定内测必须解决

| ID  | 问题、证据                                                               | 改造与验收                                                                              |
| --- | ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| F06 | telemetry/useAlerts/useUwb是全局状态；首页以liveForPet ?? latest兜底动作 | 按当前user/pet/device维护状态；两设备交错不会让另一只宠物动作、告警、轨迹变化           |
| F07 | 首页load和切宠请求无代次检查，profile保留旧结果                          | 统一请求缓存键、取消和响应代次；切账号/快速切宠/慢响应只能更新当前页面上下文            |
| F08 | 首页回退旧online和体征；固件健康UART无超时失效；分类器沿用旧动作         | 区分网络接收时间、传感器测量时间、预测窗口；停止UART但保留MQTT时体征应过期              |
| F09 | 告警按帧数计数，配置基于2秒一帧但固件已10Hz；只在App组件挂载时运行       | 按持续时间和独立样本去抖；服务端保存告警并处理通知；相同输入不同分批得相同结果          |
| F10 | create.tsx:299先建宠物再AI，后续失败重试会重新建宠物                     | 保存已创建petId，创建与生成解耦；后续任一步失败重试都只保留一只宠物                     |
| F11 | AI/日记同步阻塞请求，任务不持久保存；页面关闭后仍可能router.back         | 后台job状态机、幂等键、独立重试；卸载不反向导航，重开/重启能继续查结果                  |
| F12 | diary-post前端发petId，后端读pet_id；日记网络异常访问未赋值response      | 统一契约及异常模型；帖子关联当前宠物，超时/502/非JSON均有稳定错误结果                   |
| F13 | comment-sheet POST成功后GET失败保留草稿，重试生成重复评论                | 写操作结果单独确认，刷新失败不重发；模拟POST成功+GET500只写一次                         |
| F14 | 全局SQLite cursor被MQTT与HTTP线程共用                                    | 每操作独立connection/cursor，明确写入边界；持续写入并发查询不串结果、不报cursor错误     |
| F15 | MQTT回调逐个同步socket.send，一个慢连接可能阻塞采集                      | 采集与发送解耦，每连接有界队列；停止读取的客户端不拖慢正常用户                          |
| F16 | 全部topic共用10000条环形readings，10Hz单设备仅约16.7分钟                 | 瞬时缓存与历史记录分开，定义聚合和保留；多设备全天输入仍能查正确历史覆盖                |
| F17 | 模块导入即启动固定client ID的MQTT；状态只在单进程内                      | 独立collector后再扩HTTP/WS进程；两个Web worker不能变成两个竞争的采集客户端              |
| F18 | Collection只按传入session关联帧，未核对session对应设备；上传锁仅进程内   | 规范会话/设备关系和组合约束，上传状态可并发协调；交错设备、重复分块不串会话、不损坏媒体 |
| F19 | 普通请求无统一超时，退出等待网络，失效会话与错误被页面各自吞掉           | 统一请求超时/取消/错误分类，本地退出立即完成；断网、超时和失效状态都有可恢复路径        |

说明：以上保留账号与设备上下文，是为了功能显示和任务关联正确，不是在本版扩展隐私审查。

## 5. 推荐结构：先模块化，不全量重写

保留Expo/React Native、Flask以及已有解析、上传、回放、分类和采集确认逻辑。

```text
App/Web：当前用户 + 当前宠物 + 当前设备 + 查询/任务状态
    ↓
模块化API：账号 / 宠物 / 设备 / 趋势 / 社区 / AI任务 / 采集
    ├─ PostgreSQL：业务关系、任务、近期事件、统计汇总
    ├─ COS：图片、视频、批次归档、模型和发布包
    └─ 后台worker：AI生成、导出、媒体处理、通知

MQTT → 独立collector → 持久记录/统计/告警 → 按设备分发给WS
```

PostgreSQL迁移的原因是事务、约束、并发和历史查询需求，不是“SQLite不能做多用户”。
先修共享cursor和查询模型；把同样的错误SQL搬到PostgreSQL不会自动正确。

首期最小实体：users、pets、devices、device_aliases、device_bindings、telemetry_events、
metric_rollups、alert_events、generation_jobs、media_assets、posts/comments/likes/follows。
用userId关联个人数据，不增加组织/成员体系；设备与宠物绑定需要时间区间，以支持换设备。

10Hz每设备每天864000帧。是否全部长期保留需要产品决定，不能无期限逐帧堆入业务表。
先确定采样、展示降采样、统计粒度和原始归档范围，再选具体分区与保留实现。

## 6. 详细实施顺序

### 第一批：核心功能纠错，P0

1. 固定两用户、两宠物、多设备的可重复输入集与预期结果。
2. 统一设备ID和路由；修时长单位、趋势聚合、显示summary和数据新鲜度。
3. 修角色卡入口、正确添加入口、日记默认值与关联字段。
4. 定位功能接真实数据；若硬件未就绪，改为明确空态或独立演示模式。

**产物：** 用户看到的数据与输入一致，首个创建/查看/生成流程可完成。
**验收：** 同一60秒输入在不同频率结果一致；两设备功能均完整；无数据不生成事实。

### 第二批：多用户、多宠物完整使用，P1

1. 建立统一activePet/activeDevice和按用户划分的客户端状态。
2. 修账号切换、请求乱序、宠物选择保持、退出和页面卸载行为。
3. 补宠物编辑/删除、设备换绑、资料编辑等真实用户必需流程。
4. 完成全局loading/error/empty/retry交互规范。

**产物：** 新用户不依赖演示账号和开发人员手动改数据库即可使用。
**验收：** 注册→建宠→配对→看体征/趋势→切宠→修改资料→退出重登，三端一致。

### 第三批：后台任务与业务一致性，P1

1. AI、日记、导出改持久job，返回任务ID，支持查询、重试与结果恢复。
2. 建宠和生成拆开；发帖/评论/点赞/关注采用幂等提交及规范结果。
3. 统一前后端字段和错误模型，加入契约测试。
4. 上传/发布/生成各阶段明确处理中、成功、失败和取消语义。

**产物：** 网络失败和重复点击不会重复创建实体或丢失生成结果。
**验收：** 在每个阶段中断网络或重启进程，结果仍可找到，重放请求不重复执行副作用。

### 第四批：采集与服务运行稳定化，P1

1. collector从Web进程拆出；数据库会话和WS发送队列独立。
2. 修采样时间、去重、boot/seq、告警时间窗口及传感器超时。
3. 定义原始数据/汇总的存储策略，版本化迁移到PostgreSQL。
4. 扩多Web worker之前验证进程间状态和分发；将告警从App迁到服务端。

**产物：** 增加设备、慢客户端和常见进程故障不会让整个应用失去实时能力。
**验收：** 1/10/50台模拟设备分档测试，记录吞吐、积压、端到端延迟及数据库增长；
collector/worker重启、慢WS和上游AI故障不影响其他核心流程。

### 第五批：产品体验和交付效率，P2

1. 完成社区分页搜索、详情、举报、列表同步和分享链接。
2. COS承载媒体；发布包与模型分离，评估TAT替代SSH执行。
3. 配置staging、结构化日志、错误追踪、任务/采集指标与告警。
4. 补原生真机、Web跨域、弱网和长时间运行测试。

**产物：** 可持续交付且问题可定位，不需要开发者一直盯服务器维持演示。
**验收：** 约定容量下连续运行与发布验证通过，有可重复的核心E2E和故障处理记录。

上述是工作依赖顺序，不要求所有事情串行：AI后台与部分UI可并行；但多设备测试依赖设备ID
统一，正确历史迁移依赖单位/归属规则明确，多worker依赖collector拆分。
