# 单宠物资料管理设计

日期：2026-10-25
分支：codex/pet-profile-management
状态：方案 A 已由用户选择；本文待用户确认后进入实现。

## 目标与范围

把当前只支持创建的宠物档案完善为可查看、编辑、保存并在各页面一致展示的管理流程。继续遵守一账号一只宠物、一台设备。基础资料由 PetSense 数据库保存，读取不依赖 AI 服务。

本次覆盖名字、物种（狗/猫/兔）、品种、照片头像与 Emoji 默认头像；沿用已有字段，不增加无数据基础的年龄、性别、体重和健康结论。不加入删除档案、多宠物切换、趋势修改、动作识别或新的 AI 生成流程。

## 方案取舍

- A：完善现有单宠物管理。增加档案详情/编辑、服务端更新接口、头像上传和统一刷新；用户已选择此方案。
- B：多宠物管理。需要同步改变账号限制、当前宠物选择、设备归属及多个聚合接口；用户本次未选择。
- A 内部采用独立档案页面，保留 setup 负责首次建档和设备绑定。把所有编辑继续塞进 setup 会混淆“保存资料”和“绑定设备”，所以不采用。

## 已确认的问题

1. 宠物档案卡片无点击行为；服务端只有创建接口，没有资料修改接口。
2. 用户主页中的宠物另行手写序列化，缺少 avatarImageUrl 等字段，与列表、首页不一致。
3. create 的“添加宠物”入口对已有档案也进入 setup 完成页，文案不符合实际行为。
4. 各页面独立取数，编辑后没有明确的资料失效通知。
5. 首页已读取数据库名字，不能把所有旧名字都归因于硬编码。PetGIF 的名字、生成文字和图片属于另一份资料，不能静默当成可编辑的基础档案。

## 页面与交互

### 入口

- “我的 → 宠物档案”整张卡片可点击，显示照片/默认头像、名字、中文物种和品种、管理提示及箭头；设备编码留在设备区域，避免占据资料摘要。
- 首页宠物头像提供明确的“宠物资料”可访问名称及轻量管理入口，不改变其在线状态和告警环语义。
- create 的宠物入口统一叫“宠物档案”，由档案页面判断已有/未建档状态，避免请求完成前闪现错误的“添加”文案。
- 无档案时显示建档说明和“建立宠物档案”，进入现有 setup；加载失败显示重试，不误判成无宠物。

### 档案详情

独立 `/pet` 页面，沿用项目主题、圆角卡片和宽屏居中规则。顶部返回和“编辑”操作；上方为头像、名字及中文物种/品种，下面分组展示基本资料和项圈状态。品种为空显示“未填写”，不推断品种；未知物种显示中性兜底。

设备已绑定时展示编码、在线状态和真实电量（0% 合法）；未绑定显示“绑定项圈”引导到 setup。绑定/解绑仍由现有设备流程处理，编辑资料不会更改设备关联。

### 编辑

进入编辑时从最新已加载档案建立本地草稿。字段为名字（必填，去首尾空白后 1—20 个 Unicode 字符）、物种（狗/猫/兔）、品种（可选，最多 40 个 Unicode 字符），以及头像。

头像可选择本地照片、取消选择、或改用内置默认 Emoji。照片在本地预览，点击保存才上传；取消编辑不产生头像请求。头像模式明确分为保留现有、替换照片、使用默认 Emoji。保留现有照片时修改其他字段不会清空照片。

名字和品种限制使用按 Unicode 码点计数的共用客户端规则，与 Python 长度语义对应，避免中文和常用补充平面字符计数不一致。服务端仍独立验证，不依赖客户端截断。

物种更改时更新建议默认 Emoji；用户明确选择的 Emoji 不应被后台刷新覆盖。品种不随物种变化擅自删除。

保存按钮在未修改、校验失败或保存中不可重复提交。校验错误就近显示；保存失败保留草稿和照片，显示错误及重试。保存成功使用服务器返回的完整档案更新详情，显示成功反馈并退出编辑状态。

返回、Android 返回键和导航离开在有未保存变更时提供“继续编辑 / 放弃修改”；Web 关闭/刷新通过 beforeunload 提醒。保存中阻止重复保存和离开，防止用户误以为已取消但请求实际成功。取消或图库取消不清空之前的草稿。

相册使用 Expo 系统图片选择器，仅在系统确有需要时申请权限；取消没有错误提示，权限拒绝/文件不支持提供中文说明。支持 JPEG/PNG/WebP，最大 10MB；使用头像裁剪与适当压缩，避免不必要的大图。

## 服务端与数据一致性

- 新增所有权校验的 GET/PATCH `/api/app/pets/<id>`。更新只允许 name/species/breed/avatarEmoji/avatarMode 和头像文件；拒绝非预期字段，不允许修改 user_id、device_id、petgif_id。
- PATCH 支持纯字段 JSON，以及附照片的 multipart。两种路径遵守相同验证规则。图片模式为 keep/photo/emoji；photo 必须有照片，emoji 清除 avatar_image 引用但保留 Emoji。
- 在处理图片和写文件前校验登录、宠物归属、字段及头像模式。不存在或不属于用户均返回 404。
- 图片验证格式、体积及实际可解析性；可使用现有可用图片解码库，若需新依赖须说明并更新锁定配置。PNG/JPEG/WebP 以解码结果为准，不只信任扩展名或 MIME。
- 所有字段与头像作为一次保存提交；文件处理或数据库失败不产生部分字段更新。数据库提交失败清理本次新建文件。旧头像本次不自动删除，避免已有引用失效；不引入存储清理项目。
- 成功返回统一序列化的完整宠物。列表、dashboard、当前用户及公开用户页复用同一个公开字段集合，不扩大现有对外数据可见范围，不把 user_id 等私有字段加入公开档案。
- 创建和修改采用同一套基本字段验证；保留已有客户端 POST 响应兼容性。非法类型、空白名字、超长输入、非法物种必须返回明确 400，不静默把 null/对象转成字符串或截断。
- 数据库作为基础资料唯一事实来源。PetGIF 的已生成文字和图片不会自动重写；新增页面不把它们展示为已同步的可编辑基础资料，不把基础资料保存成功等同于重新生成成功。

## 客户端刷新

提供轻量资料变更通知，在创建、修改和头像保存成功后发布；首页、我的、项圈卡片、公开用户页/帖子列表在重新聚焦时重新读取，当前仍挂载且可见的档案消费者收到通知后刷新。设备绑定/解绑使用相同失效机制刷新相关状态。通知只携带版本/失效信号，账号切换时不复用上一用户的数据。

编辑过程中后台刷新不能重置草稿。请求使用取消/序列保护，旧响应不能覆盖更新后的结果。当前服务端不具备版本字段，本次不实现跨设备乐观锁；以最后一次成功保存为准。

网络错误包含响应丢失时保留草稿，更新接口重复提交相同字段应可安全重试；不把超时推断成“肯定没有保存”。成功后重新进入或重启应用应读取到数据库新值。

## 验证与验收

服务端隔离测试覆盖：未登录、他人档案访问/更新、合法中文改名、字段清空与边界、非法输入、设备关联保持、头像保留/替换/移除、非法图片和失败不部分保存、列表/dashboard/用户页一致性。

客户端测试针对关键领域行为：Unicode 验证、草稿变更判断、头像模式与保存负载、资料失效通知与账号隔离。避免只断言实现字符串的测试。

运行 app 的 lint、typecheck、format:check、已有测试及 Web 构建；运行完整 server unittest。先配置项目要求的 Python 3.12 环境，目前系统默认 Python 3.9 缺 Flask，不把此环境错误当作业务基线失败。

computer use 使用独立本地服务和可丢弃测试账号验证：首次无档案、已有档案入口、中文改名、取消修改、校验失败、保存失败重试、返回提示、头像选择取消/保存、首页及我的/项圈名字一致、重启后持久化，以及窄屏与深色样式。若图库或原生平台验证受环境限制，明确说明范围，不宣称已验证。
